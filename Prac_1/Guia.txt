Fase 1: Diseño de la Base de Datos (El "Cerebro")
Antes de las comunicaciones, necesitas decidir dónde residirá la "verdad". Dado que usarás múltiples instancias y arquitecturas, Redis es tu mejor aliado por su velocidad y atomicidad.

Modelo Numerado: Diseña una estructura en Redis (puedes usar un Hash o Strings con SETNX) donde la clave sea el asiento (1-20,000) y el valor el client_id.

Modelo No Numerado: Usa un contador atómico en Redis (INCR) que se detenga al llegar a 20,000.

Fase 2: Arquitectura de Comunicación Directa (REST/RPC)
Desarrollo del Servidor: Crea un servicio (en Python con Flask para REST o Pyro4) que reciba la petición de compra y consulte a Redis.

Implementación del Load Balancer:

Configura NGINX en una instancia de AWS para que reparta el tráfico hacia varios nodos servidores (EC2).

Cliente Directo: Crea un script que lea los archivos de benchmark y envíe peticiones HTTP/RPC al balanceador.

Fase 3: Arquitectura de Comunicación Indirecta (RabbitMQ)
Configuración de RabbitMQ: Levanta el servidor de RabbitMQ en una instancia de AWS separada.

Desarrollo del Worker: Transforma tu servidor de la Fase 2 en un "Consumidor". En lugar de escuchar HTTP, debe sacar mensajes de una cola de RabbitMQ, procesarlos contra Redis y (opcionalmente) confirmar el resultado.

Cliente Indirecto (Productor): El cliente ahora lee el benchmark y "escupe" los mensajes a la cola de RabbitMQ lo más rápido posible.

Fase 4: Despliegue en AWS Academy
Instancia de Base de Datos: Una VM para Redis + RabbitMQ.

Instancias de Carga: Una VM para el Balanceador (NGINX) o la entrada de RabbitMQ.

Instancias de Cómputo: 2 o más VMs para ejecutar los Workers/Servidores.

Instancia de Benchmark: Una VM dedicada solo a ejecutar el script del cliente para no quitar CPU a los servidores.

Fase 5: Escalamiento Dinámico y Contención (Requerimientos Adicionales)
Prueba de Escalamiento: Ejecuta el benchmark con 2 workers, luego añade 2 más en caliente y observa si el throughput sube en tus logs.

Escenario de Alta Contención: Modifica tu cliente para que el 80% de las peticiones pidan el mismo 5% de asientos (asientos del 1 al 1000). Aquí es donde verás a Redis sufrir y los tiempos de espera aumentar.

Fase 6: Evaluación y Benchmarking
Ejecución de Pruebas: Pasa los archivos benchmark_unnumbered.txt y benchmark_numbered.txt por ambas arquitecturas.

Recolección de Métricas:

Tiempo total de inicio a fin.

Operaciones por segundo (Ops/sec).

Validación de errores (asegurar que no hay asientos duplicados).

Generación de Gráficos: Usa librerías como matplotlib o Excel para comparar:

Directo vs Indirecto.

Rendimiento con 1, 2, 4 y 8 workers.

Impacto de la contención en el modelo numerado.
